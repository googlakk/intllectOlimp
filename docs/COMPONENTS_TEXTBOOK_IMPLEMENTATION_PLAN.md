# План расширения компонентов по КТП и учебнику

Дата: 29 сентября 2026 года. Статус: первый цикл реализован локально; исходный план ниже сохраняет последующие этапы. Дополняет `INTERACTIVE_COMPONENTS_RESEARCH_2026-09-29.md` и уточняет очередность с учётом главного требования владельца: каждый компонент должен помогать освоить конкретную тему урока по учебнику.

### Сделано в первом цикле

- `RuleDiscovery` и `TransformationMachine`: работающие числовые движки, собственные демо, общие серверные/клиентские проверочные случаи.
- Настоящие визуальные превью в каталоге, загрузка только около видимой области, выбор существующего урока из демо.
- Подготовка отдельного блока по выбранной цели КТП, подтверждённому параграфу или полному упражнению. В контекст входят предмет, класс, язык, место вставки и соседние блоки.
- Предпросмотр до вставки, подпись содержимого и источника, проверка актуальности, защита от повторного запроса, сохранение через существующие версии черновика. Таблиц и миграций нет.
- Новые блоки доступны генератору целого урока как варианты для подходящих числовых целей, только при наличии непустого материала учебника. Дополнительных отдельных запросов на каждый блок целого урока нет.
- Реальные платные вызовы и база не использовались; качество содержимого настоящей генерации ещё требует отдельной согласованной пробы.

### Осталось после первого цикла

- «Досье доказательств», «Слои», источники для изображений и открытые ответы.
- Более глубокая проверка смыслового соответствия содержания книге и цели; сейчас связь подтверждается идентификаторами, промптом и структурными/математическими проверками.
- Защита старого общего `PUT /blocks` от сохранения устаревшей вкладки. Новый insert защищён от конкурирующих вставок, но старое сохранение всей страницы пока может перезаписать последующие изменения.

Раздел «Пробелы» ниже описывает исходное состояние до первого цикла, а не текущие возможности.

## 1. Продуктовый результат

Компонент — интерактивное представление выбранного учебного материала на определённом этапе урока. У него есть цель КТП, источник содержания, место в уроке, действие ученика и ожидаемый учебный результат.

Один и тот же движок работает:

- при автоматическом подборе блоков во время генерации урока;
- при добавлении учителем блока в существующий урок;
- при выборе компонента в общей библиотеке с последующим выбором целевого урока.

Моковые данные используются только в демонстрации библиотеки. При добавлении в урок компонент получает содержание этого урока. Во время показа он воспроизводит сохранённое содержание и выполняет локальную логику; повторной генерации на каждый ход или открытие не требуется.

## 2. Что уже есть и чего не хватает

### Уже есть

- `backend/ai/planner.py`: цели и параметры КТП превращаются в контракт темы и план компонентов.
- `backend/services/textbook_context.py`: загрузка подтверждённых связей темы с параграфами, текста основного параграфа и элементов выбранных параграфов. Для повторения/контрольной предусмотрено обращение к изученным темам.
- `backend/ai/textbook_grounding.py`: правила использования учебника, ссылки `source_ref`, различение задачи книги, аналога и объяснения по параграфу; учёт режима показа материала книги.
- `backend/services/lessons.py:843`: генерация урока с КТП, планом и материалом учебника; сохранение метаданных источника, черновика и проверок качества.
- Общий `BlockRenderer`, редактор, режим показа на доске и система версий урока.

### Пробелы

- В `LessonBlockBuilder.tsx:95` ручное добавление копирует `componentDemos` и сразу сохраняет результат в урок. Контекст учебника к этому действию не подключён.
- Нет общего сервиса подготовки одного блока с учётом источника, цели и соседних шагов урока.
- Контекст текстовый: текст дополнительных параграфов сейчас не загружается, их элементы передаются отдельно. Текст элемента ограничивается 700 символами при подготовке промпта. Для отдельного сложного упражнения нужна адресная загрузка полного материала и обнаружение неполноты.
- Картинки, таблицы, карты и части схем не представлены в этом сервисе как готовые визуальные ресурсы компонентов. Нельзя автоматически обещать «Слои» для любого загруженного PDF.
- Наличие `source_ref` не доказывает, что содержание действительно соответствует указанной странице. Текущие проверки преимущественно эвристические; глубокие поля новых компонентов тоже потребуют проверки.
- Открытые задачи не укладываются в текущий общий ответ «верно/неверно».

## 3. Общая схема

`урок и цель КТП → подтверждённый материал учебника → подходящая механика → конфигурация блока → проверки → предпросмотр → сохранение в черновик`

Контекст и правила подготовки должны быть общими для генерации урока и ручной вставки. Это устраняет расхождение «генератор использует книгу, а каталог вставляет случайный пример».

### Контекст одного компонента

| Данные | Назначение |
|---|---|
| Тема, предмет, класс, язык | Уровень сложности и терминология |
| Выбранные `objective_ids` и тексты целей | Что именно дополняет блок |
| Этап урока | Объяснение, исследование, практика или проверка |
| Книга, параграфы, конкретные задачи/фрагменты | Источник фактов, условий, определений и чисел |
| Разрешённый способ использования | Задача книги, аналог или преобразование объяснения |
| Место вставки и краткое содержание соседних шагов | Что уже объяснено и что будет дальше |
| План урока и доступное время | Не повторять существующую активность и не перегружать урок |
| Доступные изображения и схемы | Можно ли собрать визуальный вариант из имеющихся материалов |
| Версия черновика и отпечаток источника | Обнаружить устаревший результат до вставки |

Контекст собирает сервер через существующие проверки доступа. Клиент выбирает идентификаторы, а не назначает произвольную книгу или чужой урок. Материал книги трактуется как данные, встроенные в него команды не исполняются.

## 4. Два основных сценария

### А. Генерируется весь урок

1. Загрузить контекст КТП и подтверждённых источников.
2. Определить, какими данными действительно располагаем: правило, примеры, упражнение, исторический источник, таблица, изображение.
3. Выбрать подходящий блок под цель и данные. Например, «обосновать вывод» и два источника допускают досье; одно определение без свидетельств — нет.
4. Подготовить содержимое выбранного блока в общей схеме генерации по частям. В первом варианте не добавлять обязательный отдельный платный запрос на каждый блок.
5. Проверить структуру, источник, выполнимость и соответствие этапу.
6. Сохранить блок в обычный черновик урока с остальными шагами.

Если новой механике не хватает материала, планировщик выбирает подходящий существующий блок и объясняет причину в отчёте для учителя. Нельзя придумывать источники, факты или необходимые рисунки ради использования нового компонента.

### Б. Учитель дополняет уже созданный урок

1. Нажимает «Добавить по теме» в нужном месте урока.
2. Видит выбранную цель, книгу/параграф и конкретное упражнение, если оно подходит. Может выбрать другой подтверждённый фрагмент.
3. Получает несколько совместимых механик с кратким пояснением: «Поможет увидеть порядок преобразований в примере…».
4. Выбирает «Подготовить по учебнику» либо заполняет форму вручную. Автоматическое заполнение — явное действие, связанное с расходом на генерацию; просмотр библиотеки ничего не генерирует.
5. Пробует отдельный предпросмотр. Видит источник, назначение блока, разбор и предупреждения о недостаточных данных.
6. Нажимает «Вставить в урок». Сохраняется только выбранный блок в указанное место черновика через существующую логику версий.

Генерация и вставка — разные операции. При отмене предпросмотра урок не изменяется. Перед платной операцией несохранённые правки нужно сохранить либо явно разрешить конфликт; нельзя готовить блок по незаметно устаревшему серверному состоянию.

Если во время подготовки урок или его привязка к источнику изменились, при вставке показать конфликт и предложить пересмотреть результат. Не затирать новые правки. Повторный запрос вставки не должен создавать дубликат.

В общей библиотеке кнопка «Использовать в уроке» сначала выбирает урок, затем запускает тот же сценарий. До выбора урока показанное демо остаётся демонстрацией.

## 5. Что считается содержанием из учебника

У блока должна быть понятная учителю карточка происхождения: книга, параграф/страница, номер задания, цель, характер адаптации.

Три вида:

1. **По определению/объяснению:** терминология и смысл сохраняются, интерактив показывает связи или преобразования.
2. **По задаче книги:** условие и допустимый способ использования сохраняются; интерфейс помогает решить ту же предметную задачу.
3. **Аналог задачи:** явно помечен как аналог, содержит ссылку на исходную задачу, сохраняет тип рассуждения и сложность.

Развивать существующий `source_ref`, сохраняя обратную совместимость. Для блока из нескольких свидетельств понадобятся множественные ссылки, включая ссылки отдельных элементов — улик, правил, подписей. Предусмотреть ID книги, параграфа, элемента, страницу и вид адаптации. Ссылки проверяются на принадлежность выбранному контексту. Метаданные связывают блок с источником, но сами по себе не являются доказательством фактической правильности.

Для воспроизводимости сохранить выбранные ссылки, версию/отпечаток использованного материала и готовую конфигурацию. Изменение распознавания книги впоследствии может вызвать уведомление учителю, но не переписывает опубликованный блок. Учительский источник и проверка не должны раскрывать ответы ученику раньше нужного этапа.

Учесть существующий `student_display`: режим показа ссылок/аналогов и разрешённого дословного материала. Не копировать весь параграф в ученический экран или метаданные ответа API.

Если учебник не распознан, не привязан либо нужный фрагмент неполон, режим «по учебнику» показывает точную причину и действие: выбрать параграф, подготовить страницы, проверить распознанное условие. Учитель может отдельно добавить собственный материал с соответствующей пометкой. Нельзя молча подменять книгу общими знаниями модели. Платное распознавание не запускается автоматически.

## 6. Порядок внедрения

| Этап | Что делаем | Проверяемый результат |
|---|---|---|
| 1. Контекст и источники | Единый сбор контекста выбранной цели, полное выбранное упражнение, признаки неполноты, ссылки и отпечаток | Понятно, какие данные книги реально попадут в блок |
| 2. Добавление по теме | Подготовка одного блока, предпросмотр, вставка в черновик, конфликт версий, форма источника | Учитель добавляет подходящий существующий блок без попадания демо в урок |
| 3. Два первых новых движка | «Скрытое правило» и «Фабрика преобразований», формы учителя, схемы данных, проверки | Один движок работает на разных темах с разным материалом книги |
| 4. Источники и визуальные материалы | «Детективное досье»; подготовленные шаблоны «Слоёв» при наличии необходимых материалов | Новые форматы работают с реальными свидетельствами и схемами |
| 5. Выбор в генераторе | Подбор по цели и наличию данных, предметные профили, бюджет интерактивов, педагогическая связность | Новые блоки появляются в подходящих местах нового урока |
| 6. Показ и пилот | Общее управление учителя, показ источника в редакторе, сброс/пауза/разбор, проверка уроков | Учитель самостоятельно готовит и проводит урок на одной доске |

Интеграционные точки и схемы для автоматической генерации проектируются на этапах 1–3, а автоматический выбор новых механик включается после проверки наполнения. Первый сквозной сценарий разумно провести на существующем WorkedExample: это проверит путь «источник → отдельный блок → урок» до добавления нового сложного движка.

### Первый набор с учётом учебника

**Скрытое правило.** Из определения или правила берутся свойства и допустимые преобразования. Движок создаёт проверенные примеры/контрпримеры. Начать с числовых и геометрических правил; языковые варианты — на подготовленном словаре.

**Фабрика преобразований.** Из разобранного примера или упражнения берутся входные данные, разрешённые действия и цель. Вычисление выполняет проверенный движок. Ученику показывается ход преобразования. Начать с арифметических операций и преобразований простых фигур.

**Детективное досье.** Улики формируются из выбранных фактов и фрагментов источников. Каждый факт имеет происхождение. Если параграф не содержит конкурирующих свидетельств, не придумывать их: выбрать другой формат. Смысловые выводы и противоречия требуют просмотра учителя.

**Слои смысла.** Строятся из подготовленной схемы/карты или типизированных векторных объектов, соответствующих тексту. Распознавание PDF не означает автоматической готовности слоёв. Первая версия использует небольшой набор проверенных визуальных шаблонов; извлечение и подготовку произвольных рисунков планировать отдельно.

**Позже — штаб ресурсов и ритм.** Подключать, когда книга и КТП действительно дают подходящие величины/ограничения либо ритмический материал. Не вводить экономические коэффициенты и сюжетные факты от имени учебника.

## 7. Встраивание в текущую архитектуру

Предлагаемые границы, названия новых файлов уточняются при реализации:

- Расширить `services/textbook_context.py` адресной подготовкой материала, переиспользуя подтверждённые связи и права.
- Выделить сервис подготовки компонента, например `services/lesson_components.py`: контекст → запрос генератору → проверки → результат предпросмотра. HTTP-маршрут остаётся тонким адаптером с существующими проверками прав.
- Добавить отдельную схему подготовки одного блока в `ai/`, используя существующего провайдера, модельный выбор и общие правила источников. Генерация выдаёт конфигурацию, не исполняемый код.
- Для длительного вызова модели не держать транзакцию БД открытой: прочитать контекст, выполнить генерацию, повторно проверить версию при принятии результата.
- Расширить `component_registry.json` и точечные метаданные применимости: необходимые материалы, поддерживаемые действия, схемы конфигурации, ограничения.
- Подключить выбор в `ai/planner.py` и предметных профилях. Обновить список разрешённых компонентов и проверки генератора согласованно.
- В `features/lessonEditor/` добавить интерфейс подготовки блока. `componentDemos` оставить для библиотеки; отдельные чистые шаблоны и формы использовать для авторства.
- Вставку проводить через существующую нормализацию документа урока, управление черновиками и версионирование. Сохранять связи с эпизодами, стабильные идентификаторы и смысловые привязки; обновлять связанные реплики/медиа только там, где содержание действительно изменилось.
- Новые компоненты добавить в общий `BlockRenderer`, чтобы одна реализация работала у ученика, в редакторе и на доске. Режим показа не пишет попытки ученика.
- Первую реализацию по возможности хранить в существующих JSON-данных блока/версии; необходимость новых таблиц определяется отдельно. Если потребуется миграция, подготовить SQL для владельца, не применять самостоятельно.

## 8. Проверки и критерии готовности

### Источник

- Передаётся нужная цель и только разрешённые материалы темы.
- Параграф отсутствует, OCR пустой, задача обрезана, не хватает изображения — явный диагностируемый результат.
- Ссылка принадлежит выбранной книге и материалу, аналог помечен, несколько улик имеют свои источники.
- Вложенные поля нового блока охвачены проверками; ложная ссылка не делает выдуманный факт достоверным.

### Механика и учебный смысл

- Задача решаема; операции и критерий результата согласованы; нет посторонних данных демо.
- Контрольные примеры подтверждают работу движка; открытые задания оцениваются по критериям/учителем, не по нажатию «завершить».
- Учитель видит, какую часть параграфа блок поясняет и зачем он стоит после предыдущего шага.
- Содержание не выходит за необходимые предварительные знания и не дублирует соседние блоки без учебной причины.

### Сохранение и интерфейс

- Отмена предпросмотра не меняет урок; вставка меняет нужный черновик; повтор не создаёт дубликат.
- Устаревший результат не затирает новые правки; опубликованная версия и закреплённые за ней попытки сохраняются.
- Открытие каталога и показ готового блока не вызывают платную генерацию.
- Полноценный блок работает на доске, клавиатурой и на телефоне; ответы раскрываются по команде.

Сначала тесты с подменой БД и модели и подготовленными фрагментами источников. Затем, только с согласия владельца, небольшая платная проба на выбранных темах и ручная сверка с книгой. Предварительный набор для пилота: два первых движка × три разных подходящих темы. Это проверка адаптируемости, не доказательство общего повышения успеваемости.

Перед каждым коммитом: backend pytest, `pnpm run check:architecture`, `pnpm run check:quality`. После изменений бэкенда напоминать перезапустить локальный сервер. Прод — только после «выкладывай». Реальные данные для тестов не изменять.

## 9. Минимальный законченный результат первого цикла

Учитель открывает конкретный урок, выбирает цель и задачу/фрагмент учебника, получает содержательно подходящий интерактив, пробует его и вставляет в черновик. Ученик видит продолжение изучаемой темы; учитель может проверить происхождение материала. Этот путь должен работать и для выбранного вручную компонента, и для того же компонента в автоматически сгенерированном уроке.

Количество новых движков вторично по отношению к этому сквозному сценарию. Сначала доводим его до готовности, затем расширяем библиотеку на той же основе.
