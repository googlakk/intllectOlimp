# Передача разработки в Claude Code

Дата: 2026-09-24, Asia/Bishkek. Этот документ — контекст и ориентир; текущие файлы и свежие проверки важнее исторических отчётов.

## 1. Чего хочет пользователь сейчас

Проект — школьная учебная платформа. Учитель импортирует КТП или создаёт программу, готовит ИИ-черновик материалов, редактирует и публикует; ученик изучает, практикуется, проходит проверку, разбирает ошибки. Пользователь сообщил о сдаче проекта завтра и ограниченном лимите Codex.

Последнее согласованное направление перед переносом: улучшать существующий конструктор материалов и библиотеку компонентов, чтобы объяснения сразу были визуальными, а прохождение ощущалось как исследование/лаборатория. Не строить очередную отдельную платформу. Не сводить работу к массовой генерации старых текстовых уроков. Начать с ограниченного, работающего сквозного улучшения.

Пользователю понравились сюжетные иллюстрации и наглядность трёх образцов. Но семь сцен — ручной выбор образцов, не универсальный контракт. Количество и последовательность зависят от предмета, целей, сложности и типа занятия. Для истории подходят источники, схемы, причинные связи; для физики — прогноз, опыт, объяснение, применение. Сохранять привычное управление, разнообразить содержание.

Пользователь просит сообщать, если генерация изображений/видео исчерпает лимит. Реагировать на фактическую ошибку провайдера; не обещать знание остатка лимита, которого API не возвращает. Не включать дорогую массовую генерацию в фоне.

## 3. Что уже существует

### Основной продукт

FastAPI + async SQLAlchemy/asyncpg, PostgreSQL/Supabase, Supabase Auth/Storage; React + TypeScript + Vite + Wouter + TanStack Query. Монорепозиторий pnpm.

В предыдущей работе реализованы большие изменения учебного цикла: типы study/review/assessment/reflection/project, создание программы/раздела/темы, охват предыдущих тем, архив/восстановление, черновики и опубликованные версии, закрепление попытки за версией, история попыток, серверная проверка самоконтрольных, рекомендации и разбор ошибок. Подробности: `docs/LEARNING_CYCLE.md`. Это описание намерений и выполненного кода, не гарантия отсутствия регрессий; см. открытые риски ниже.

Правила, которые нельзя разрушить:

- Учитель работает только с доступными ему курсами/учениками; ученик не получает чужие результаты.
- ИИ создаёт черновик; публикация явная. Правки/перегенерация не заменяют опубликованное содержание молча.
- Начатая попытка остаётся на своей версии; повторная отправка результата не создаёт новую попытку/освоение.
- Архивирование сохраняет историю, убирает тему из активного маршрута и запрещает новые попытки; восстановление — в черновик.
- Контрольная проверяет навыки предыдущих тем, не создаёт «навык освоения контрольной»; разбор ошибок — отдельное назначение.
- Просмотр объяснения не равен доказанному освоению навыка.
- Нет обязательного таймера, строгого экзаменационного режима и жёсткой блокировки опубликованных тем.

## 5. Важный инцидент запуска/базы

Ранее пользователь не мог войти: frontend работал, backend на5000 отсутствовал. После запуска обнаружились недостающие колонки учебного цикла в существующей удалённой базе. В `backend/schema_compat.py` добавлена совместимость: covered_topic_ids, source_assessment_topic_id, archived_at, review_required, published_version_id, progress.responses, индексы/ограничения и backfill. При запуске backend эти additive-изменения были применены к настроенной базе. Таблица попыток могла создаваться через create_all.

НЕ считать, что полная миграция `supabase/migrations/20260924122116_learning_cycle.sql` и semantic repair уже выполнены. Они не запускались целиком в этой работе. Документ LEARNING_CYCLE описывает порядок развёртывания; фактическая текущая база также получила runtime-совместимость. Сначала выяснить состояние схемы, сделать резервную копию, проверить на копии; не запускать миграции/repair --apply автоматически.

`backend/main.py` при старте вызывает `Base.metadata.create_all` и `apply_schema_compatibility`. Значит даже «просто запустить» backend против другой базы может менять схему. Повторный bootstrap администратора и смена Supabase-настроек не нужны для продолжения в существующей среде.

При подготовке передачи lsof показывал Python PID81571 на5000, но слушателя5173 не показал. Это только снимок, PID может устареть. Проверь процессы заново; не убивай все node/python. Здесь серверы не перезапускались.

## 6. Открытые риски — проверить, не объявлять уже исправленными

Предыдущая работа прерывалась. Есть незавершённые вопросы основного учебного цикла, не связанные с образцами:

1. `AssessmentExperience.tsx`: debounce1200мс, cleanup отменяет таймер. Уход со страницы до сохранения может терять последние ответы. Проверить также изменения во время pending-запроса, порядок сохранения и завершение.
2. `progressSaver.ts`: pending payload очищается перед запросом; onError не видно восстановления очереди. Проверить повтор сохранения после ошибки и преждевременное отображение завершения в окружающем UI.
3. `LearningContext.tsx` при передаче читает текущий source manifest/progress и проверяет status===completed, без видимого fallback к последней завершённой истории. После restart контрольной прежний разбор может пропадать; особенно важны архив и смена опубликованной версии.
4. Таблица истории имеет attempt_number, но это не доказательство защиты от запоздалого save предыдущей попытки после restart. Проверить контракт save/restart и явную идентификацию попытки. При чтении `backend/routes/progress.py` отдельного поля attempt_number в save не обнаружено.
5. `list_attempts` возвращает snapshot/version ID; вопрос отображения прежних заданий/объяснений после новой публикации требует проверки. Не подставлять вопросы текущей версии к старым ответам.

Это выявленные при чтении риски, а не свежие end-to-end доказательства всех отказов. Сначала воспроизвести тестом. Не расширять текущую задачу без необходимости, но не обещать надёжное сохранение без проверки этих путей.

## 8. Предлагаемая следующая небольшая поставка

1. Прочитать конструктор/генератор и проверить запуск, вход и baseline.
2. Взять один обычный урок из программы и пройти путь редактор→черновик→предпросмотр→публикация→ученик→результат, зафиксировав реальные проблемы.
3. Улучшить существующие ShortExplanation/Presentation/WorkedExample и интерактивный блок: крупный визуал, короткие порции текста, действия и обратная связь. Сохранять поддержку старых DTO и всех существующих блоков.
4. Расширять typed-план генерации нужными визуальными полями и медиа-намерением; точные диаграммы/формулы — программно, картинки — для сюжета/контекста. Не давать модели генерировать исполняемый произвольный JS.
5. Если используются настоящие image/video API: сохранять отдельный статус задачи, текущий черновик при сбое, понятную ошибку/повтор при quota. Не считать наличие настроек провайдера доказательством работающей генерации.
6. Обновить внешний вид каталога и реальные ученические компоненты совместно. Переносить принципы образцов, а не копировать hardcoded сценарии и localStorage в основной учебный прогресс.
7. Закончить одним реальным уроком из конструктора с опубликованной версией и проверенным сохранением. Не мигрировать/перегенерировать все материалы и не запускать новый масштабный рефакторинг перед сдачей.

Предпочтения пользователя: русский язык, понятные краткие объяснения; действовать самостоятельно в согласованной области, не спрашивать повторно очевидные разрешения; не скрывать непроверенные места, ошибки сохранения и ограничения генерации.
